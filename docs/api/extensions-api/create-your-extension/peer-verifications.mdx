Create a standalone review of a privately uploaded image from your extension backend. Chaster presents the checks to the community, an eligible keyholder or experimental AI, stores the verdict and runs your configured rejection actions. Neither the native Verification Picture extension nor the Penalties extension is required.

This differs from [requesting a native verification picture](/api/extensions-api/interact-with-extensions/verification-picture), which asks the wearer to submit a photo through that extension. Here, your backend already has the image and creates its own review.

## Declare verification kinds

In the Developer interface, open your application and extension, then add verification kinds in its settings. Each kind describes a review purpose. Declare the kind before using its key in a creation request.

The extension settings field has this shape:

```json
{
  "verificationTypes": [
    {
      "key": "photo",
      "label": "Photo review",
      "description": "Review a submitted synthetic photo."
    }
  ]
}
```

If you use the extensions SDK, add the same declaration to your existing `defineManifest` input, then use your normal `cx sync` workflow:

```typescript
import { defineManifest } from "@chasterapp/extension-server";
import { extension } from "./extension";

export default defineManifest(extension, {
  displayName: "Synthetic extension",
  subtitle: "A synthetic review example",
  summary: "Review submitted photos",
  availableModes: ["unlimited"],
  defaultRegularity: 3600,
  verificationTypes: [
    {
      key: "photo",
      label: "Photo review",
      description: "Review a submitted synthetic photo.",
    },
  ],
});
```

Use the export and path of your own extension definition in place of `./extension`.

Keys are unique within an extension and match `^[a-z0-9-_]{1,40}$`. Labels contain 1 to 60 characters. Optional descriptions contain at most 300 characters. Labels and descriptions are plain text.

When updating extension settings or syncing a manifest, omitting `verificationTypes` preserves the remote declaration, `[]` clears it, and `null` is invalid. Removing or renaming a key affects future creation. Existing reviews retain the kind and check labels stored when they were created. The declaration array `verificationTypes` is separate from the singular `verificationType` in a review response.

## Upload and create a review

First [upload a private image](/api/extensions-api/create-your-extension/files) and keep the returned `attachmentToken` on your backend. Then send `POST /api/extensions/sessions/:sessionId/peer-verifications` using the same application's [developer bearer token](/api/extensions-api/authentication) and the same session. The lock must be active.

Save the following synthetic request as `review.json`, replacing the attachment placeholder with the returned token:

```json
{
  "verificationTypeKey": "photo",
  "attachmentToken": "<ATTACHMENT_TOKEN>",
  "visibility": "all_members",
  "delay": 900,
  "maxVotes": 3,
  "checks": [
    {
      "name": "generic",
      "id": "seal-intact",
      "title": "Seal intact",
      "description": "Inspect the synthetic seal.",
      "rejectionReasons": [
        {
          "slug": "unclear",
          "text": "The seal is unclear."
        }
      ]
    },
    {
      "name": "generic",
      "id": "date-visible",
      "title": "Date visible",
      "description": "Check the synthetic date card.",
      "rejectionReasons": [
        {
          "slug": "unclear",
          "text": "The date is unclear."
        }
      ]
    }
  ],
  "punishments": [
    {
      "name": "add_time",
      "params": 3600
    }
  ]
}
```

```bash
curl --request POST \
  'https://api.chaster.app/api/extensions/sessions/synthetic-session-01/peer-verifications' \
  --header 'Authorization: Bearer <DEVELOPER_TOKEN>' \
  --header 'Content-Type: application/json' \
  --data-binary @review.json
```

Each generic check requires a nonempty, review-wide unique `id`, a plain-text `title` (1 to 60 characters), a required plain-text `description` (0 to 300 characters), and a nonempty `rejectionReasons` array. Each reason requires nonempty `slug` and `text` strings. Slugs must be unique within a check. Different checks can reuse `unclear`, as above: the seal and date have different stored reason text and separate counts.

Built-in `task`, `chastity_device` and `bondage` check families remain supported. A single built-in entry can omit `id`; repeated entries of the same family need explicit, distinct IDs. Built-ins expand into subchecks. Use the returned criterion IDs; do not reconstruct or parse them.

The `punishments` array uses the seven existing [lock actions](/api/extensions-api/create-your-extension/lock-actions): `add_time`, `remove_time`, `freeze`, `unfreeze`, `toggle_freeze`, `pillory`, and `set_display_remaining_time`. Time values are in seconds. It defaults to `[]`. Chaster snapshots this list and executes it on rejection; your verdict handler must not run it again.

:::caution Ambiguous creation
Creation, notification and media retention are sequential. A disconnected or failed POST may already have created a review. There is no creation idempotency key or exact request-correlation field. Save a successful response's `_id`; if the outcome is uncertain, inspect session history before considering a retry. History cannot identify your original request exactly, and retrying can create a duplicate.
:::

## Audience and completion rules

For `visibility: "all_members"`, community voting lasts `delay` seconds: an integer from 900 to 21600, default 21600 (six hours). Optional `maxVotes` is an integer from 3 to 100; omit it for no vote cap. Completion occurs when the window expires or the vote cap is reached. At least 75% approving votes produces `verified`; otherwise the verdict is `rejected`.

A community timeout with zero votes produces `verified`. It does not invent approvals for unanswered criteria: their counts stay zero.

For `visibility: "keyholder"`, the eligible keyholder reviews the image. There is no timeout. Valid community `delay` and `maxVotes` values are ignored for that audience, and history shows `endsAt: null` and `maxVotes: null`. A missing or ineligible keyholder returns 409, with no community fallback or automatic success.

## Experimental AI reviews

Use `visibility: "ai"` on the same standalone creation endpoint for built-in `task`, `chastity_device` or `bondage` checks, or generic checks. The declared kind, active-lock ownership, authentication and wearer suspension restrictions still apply.

:::caution Experimental AI review
AI review is experimental. Your image is sent to an external AI service for processing. AI can make mistakes, and a rejected review can trigger configured punishments.
:::

Display an equivalent warning before photo capture or submission in your partner-owned interface. Chaster cannot enforce that warning in a third-party interface. Explain the configured rejection actions before the wearer submits their image.

AI is available when the current wearer **or** current keyholder belongs to the eligible experimental cohort. An eligible wearer does not need a keyholder. Eligibility is evaluated on every request, regardless of stored configuration, developer identity or an earlier availability response, and is checked again during processing.

This synthetic built-in request uses a task criterion. Replace `SYNTHETIC_ATTACHMENT_TOKEN` with the signed attachment credential from your private upload:

```json
{
  "verificationTypeKey": "photo",
  "attachmentToken": "SYNTHETIC_ATTACHMENT_TOKEN",
  "visibility": "ai",
  "checks": [
    {
      "name": "task",
      "task": "Show the requested item"
    }
  ]
}
```

This independent generic alternative preserves its custom criterion ID and exact reason set:

```json
{
  "verificationTypeKey": "photo",
  "attachmentToken": "SYNTHETIC_ATTACHMENT_TOKEN",
  "visibility": "ai",
  "checks": [
    {
      "name": "generic",
      "id": "seal",
      "title": "Seal",
      "description": "Inspect",
      "rejectionReasons": [
        {
          "slug": "unclear",
          "text": "Seal unclear"
        }
      ]
    }
  ]
}
```

Generic IDs, criterion-local custom reasons and stored source identity have the same meaning as in human reviews. Do not substitute built-in reason slugs for your generic reasons. Chaster selects the model and provider through backend operational configuration; partners submit no model or provider field.

AI has no community voting timer or quorum. Valid human `delay` and `maxVotes` settings are ignored: creation has `endsAt: null`, and history has `maxVotes: null`. Save the returned `_id` just as for a human review.

When neither participant qualifies, creation returns **403 Forbidden**:

```json
{
  "statusCode": 403,
  "message": "AI review is unavailable for this lock.",
  "error": "Forbidden"
}
```

This eligibility check happens before attachment validation, review creation, changes to media expiry/retention or queueing. No review or processing job is created and the original image expiry is unchanged. There is no keyholder or community fallback.

Choosing `visibility: "keyholder"` still returns **409 Conflict** when that reviewer is missing or ineligible:

```json
{
  "statusCode": 409,
  "message": "Keyholder reviewer is unavailable",
  "error": "Conflict"
}
```

Chaster makes bounded AI processing retries. Failed or exhausted processing can end as `unavailable`; loss of eligibility before completion can do the same. A validated AI rejection remains `rejected` and can trigger the snapshotted punishments. It is not a processing error to retry. There is no automatic approval, rejection or human fallback for an unavailable result.

Processing retries are separate from webhook delivery retries and your creation requests. Do not blindly retry a disconnected or failed creation POST: it may have persisted a review, and resubmitting can create a duplicate. Save any returned ID, inspect history and assess duplication before deciding whether to submit again. History cannot prove exact request correlation.

## Search all session history

`POST /api/extensions/sessions/:sessionId/peer-verifications/search` returns **200 OK**, scoped to both the creating partner and session. History remains readable after lock end while that session exists; a deleted session returns 404.

For all statuses and kinds, including retired kinds, send `{}`. Omitted or empty filters do not narrow results. To filter, save this as `search.json`:

```json
{
  "criteria": {
    "statuses": ["ongoing", "verified", "rejected", "unavailable"],
    "verificationTypeKeys": ["photo"]
  },
  "limit": 1
}
```

```bash
curl --request POST \
  'https://api.chaster.app/api/extensions/sessions/synthetic-session-01/peer-verifications/search' \
  --header 'Authorization: Bearer <DEVELOPER_TOKEN>' \
  --header 'Content-Type: application/json' \
  --data-binary @search.json
```

`limit` defaults to 20 and accepts integers from 1 to 100. Results are sorted by descending `_id`. The following example shows a page with one completed review and another page available:

```json
    "verificationTypeKeys": ["photo"]
  },
  "limit": 1,
  "cursor": "000000000000000000000301"

```

Stop when `hasMore` is false; the final page omits `nextCursor`. This cursor must be a 24-character ObjectId string. Review-history pages do not return a total `count` or use the session-search `paginationLastId` convention.

History rows include timestamps, source, stored kind/check labels, snapshotted punishments, nullable `maxVotes` and vote totals. They exclude media credentials and voter identities. Top-level `nbVerifiedVotes`, `nbRejectedVotes` and `rejectionReasons[].nbVotes` remain present alongside `voteCounts`.

The criterion result shapes differ by surface:

| Surface                      | Criterion totals                     | Criterion reason totals      |
| ---------------------------- | ------------------------------------ | ---------------------------- |
| Creation and verdict webhook | `nbVerifiedVotes`, `nbRejectedVotes` | `rejectionReasons[].nbVotes` |
| History                      | `approved`, `rejected`               | `rejectionReasons[].count`   |

Preserve `checkId`, `checkIndex` and `subcheckName`. Creation/webhook `name` is the family; history `name` is the subcheck name. For generic checks, both names are `generic`. Counts belong to each criterion, including when reason slugs repeat. The example's seal has three approvals while the date has two: the overall review is rejected with only two approving votes out of three.

### Unavailable AI outcomes

History filters accept `ongoing`, `verified`, `rejected` and `unavailable`; use `{}` to include all statuses and kinds. Continue pagination with the same filters, including `unavailable` when you need it.

An unavailable review is terminal with an `endedAt`, zero overall and criterion counts, and empty counted rejection reasons. Its declared `checks[].rejectionReasons` remain stored. It causes no rejection punishment and does not automatically approve, reject or switch to a human audience. Real `verified` and `rejected` outcomes keep their existing semantics.

These are **independent alternatives**, reusing a synthetic review ID to illustrate two possible outcomes, not successive states of one review. Each is a complete final page with `hasMore: false` and no `nextCursor`.

## Errors

| Status | Situation                                                                                                                                                                                   |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 400    | Invalid request, undeclared kind, invalid checks/actions, or inactive lock on creation (`You cannot modify an unlocked lock.`). Invalid history filters, limits or cursors also return 400. |
| 403    | AI cohort eligibility unavailable, wearer suspended from peer verifications, or invalid/expired attachment credential (including native upload tokens).                                     |
| 404    | Foreign, expired, missing or deleted attachment resource; missing/deleted or unauthorized session.                                                                                          |
| 409    | Requested keyholder reviewer is missing or ineligible.                                                                                                                                      |

Normal authentication and rate-limit checks also apply. Failed validation does not retain the uploaded image; its original expiry remains.

## Handle the verdict

Configure your extension's callback and handle [`peer_verification.ended`](/api/extensions-api/create-your-extension/webhooks#peer-review-verdicts). It targets only the creating extension/session. Deduplicate your own work using the review ID and event name, tolerate callbacks after lock/session termination, and leave rejection actions to Chaster. History helps inspect the stored outcome; it is not a callback-repair API.
